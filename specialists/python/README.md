# nanodevs / python specialist: training-task factory

Deterministic, original, sandbox-validated Python coding tasks for fine-tuning the `python` specialist.
No model calls, no network. Every task ships a starting code base, hidden tests and a reference solution, and
`validate.py` proves that the starting code FAILS the hidden tests and the reference PASSES them.

Files

| file | purpose |
|---|---|
| `tasks.jsonl` | the dataset, one JSON object per line (schema below), generated by `build.py` |
| `tasks_fix.py`, `tasks_write.py`, `tasks_write2.py`, `tasks_feature.py`, `tasks_refactor.py`, `tasks_extra.py` | task sources (Python lists of dicts) |
| `common.py` | Docker sandbox runner (`run_files`, same limits as `phase0/harness2.py`) and task constructors `fix`, `feat`, `task` |
| `registry.py` | collects all `TASKS_*` lists |
| `validate.py` | proves every task (see below), also writes `start_outputs.json` |
| `build.py` | writes `tasks.jsonl` and prints counts |
| `tmp/` | scratch dir for sandbox runs (can be deleted) |

Workflow: `python3 validate.py` (all tasks, ~10 minutes, one container at a time) then `python3 build.py`.
`python3 validate.py <id-substring> ...` checks a subset (does not rewrite `start_outputs.json`).

## Sandbox

`python:3.12-slim`, `--network none --read-only --cap-drop ALL --security-opt no-new-privileges --user 65534:65534
--memory 256m --cpus 1 --pids-limit 64`, working directory `/w` mounted read-only. A run is `python test_hidden.py`
inside `/w`; success is exit code 0 (plain `assert`s, no pytest). The validator puts the four checks of a task
(start/reference x hidden/visible) into one container as four sub-processes in separate directories.

## Schema (`tasks.jsonl`)

Each line is a JSON object:

| field | type | meaning |
|---|---|---|
| `id` | str | unique, `py_<kind>_<name>` |
| `kind` | str | `fix` (repair a bug), `write` (implement from a spec, stub given), `feature` (extend working code), `refactor` (restructure, keep behaviour) |
| `difficulty` | str | `easy`, `medium` or `hard` |
| `topic` | str | free-form tag (graphs, dp, parsing, heaps, tries, intervals, caching, multi-file, ...) |
| `multi_file` | bool | the task has more than one source file (starting files or reference files) |
| `files` | {name: source} | STARTING code the model sees (flat names such as `cart.py`; `write` tasks start from a stub that raises `NotImplementedError`; `fix` tasks hold the buggy code) |
| `instruction` | str | what to do. For `fix` it is a short symptom description; for the others a precise spec including names and error behaviour |
| `visible` | str | a small example test file (plain asserts) that may be shown in the prompt. Fails on the start of every `fix` task, passes on the reference of all tasks |
| `start_output` | str | `fix` only: the traceback/assertion output of `visible` on the buggy code (for a "tests fail with this output" prompt) |
| `hidden` | str | the grading tests (`test_hidden.py`); never shown. Fail on `files`, pass on `files` overlaid with `reference` |
| `reference` | {name: source} | complete new contents of every file the reference solution changes or creates (files not listed are unchanged) |

A candidate answer is a `{name: source}` dict in the same form as `reference` (this is the `# file: name.py`
block format of `phase0/harness2.py`). Grade it by writing `files` overlaid with the candidate plus `hidden` as
`test_hidden.py` into a directory and running `python test_hidden.py` in the sandbox: exit 0 = pass.

## Conventions per kind

* `fix`: hidden tests cover the bug and neighbouring behaviour; the reference is a minimal patch of the buggy files.
* `write`: the stub fixes names and signatures; the instruction states edge cases and exceptions exactly.
* `feature`: hidden tests re-check the old behaviour as well as the new behaviour (extended code must not break).
* `refactor`: starting code already works. Hidden tests assert unchanged behaviour AND the new structure (a named helper, a table,
  a base class, "no `for` statements", "nesting depth <= 3", "no `isinstance`", monkeypatching a helper to prove callers use it), so the start fails.
* Algorithm and data-structure tasks (graphs, DP, parsing, heaps, tries, intervals, union-find, segment trees, backtracking) are mostly
  `write`/`fix`; several have performance probes (recursion depth, 50k operations) that rule out naive solutions.
* Everything is synchronous and deterministic (seeded `random` where used, injected fake clocks, no wall-clock time).

## Originality

Task ids, specs, buggy code, tests and references were written for this repo; names overlap with the 50 phase0 tasks were avoided
(phase0 already covers: evaluate, topo_sort, LRU, dijkstra, parse_duration, sliding window, trie, get_path, cart coupons, retry, etc.)
and no HumanEval/MBPP/QuixBugs problem was used. Honest caveat: a number of algorithm tasks are textbook / interview-style classics
(coin change, LIS, edit distance, knapsack, n-queens, skyline, text justification, regex match, min stack, k-th largest, LCS, ...).
Their specs (extra error behaviour, tie-breaking, performance probes), tests and code are written here, not copied, but the underlying
problems are well known.
